# TeachForge 产品需求文档（PRD）

**版本：** V0.2  
**阶段：** MVP 产品定义  
**产品类型：** AI Agent 教学知识研究与课前演练平台  
**主要用户：** 高校教师、职业教育讲师、专业培训教师  
**首期验证领域：** 计算机与软件工程教学  
**文档状态：** 产品需求初稿，待原型和技术评审

---

# 1. 产品概述

## 1.1 产品定位

TeachForge 是一个帮助教师完成知识研究、理解验证、教学内容准备和课堂应对训练的 AI Agent 平台。

与传统 AI 备课助手不同，TeachForge 不以自动生成讲稿为唯一目标，而是关注教师自身能否真正理解所讲知识，以及是否具备独立向学生讲解和应对提问的能力。

产品围绕两个核心模式运行：

- **学习模式（Learn）：** 教师主导，通过资料研究、多轮对话、知识探索与内容组织，完成知识理解和教学准备。
- **演练模式（Rehearse）：** Agent 主导，通过主动提问、动态追问和反例挑战，验证教师是否能够独立解释知识并应对学生提问。

系统通过长期记忆持续积累教师的知识理解状态、历史认知问题、教学材料及实际授课反馈，使后续备课能够建立在已有知识和教学经验之上。

## 1.2 核心价值主张

**让教师在走进课堂之前，真正理解自己将要讲授的知识，并做好应对学生提问的准备。**

产品提供三类核心价值：

| 价值 | 解决的问题 |
|---|---|
| 知识内化 | 教师能够生成讲稿，但不一定真正理解全部知识 |
| 课堂应对 | 教师可能会讲基本概念，却无法应对连续追问和反例 |
| 教学积累 | 每次备课相互割裂，历史知识、讲稿和教学经验难以复用 |

## 1.3 核心设计原则

### P01：AI 服务于课前准备，不依赖课堂实时答疑

TeachForge 的主要工作发生在课前和课后。

教师应在授课前完成知识理解和演练，课堂由教师独立掌控。

系统不要求教师在学生面前实时向 AI 求助。

### P02：理解知识优先于生成内容

生成讲稿不等于教师已经掌握知识。

系统应帮助教师发现知识漏洞，并通过具体证据验证其理解情况。

### P03：学习与演练采用不同交互机制

学习模式允许自由提问、查看资料和获得解释。

演练模式由 Agent 发起挑战，教师独立回答，Agent 根据回答决定后续问题。

### P04：长期记忆必须影响后续行动

长期记忆不能只是保存聊天摘要。

系统应根据历史学习、演练和教学记录，调整后续知识解释、挑战内容和课程衔接方式。

### P05：最小可用优于功能堆砌

MVP 控制功能范围，但核心能力必须达到真实可用水平。

例如：

- 检索至少采用向量与 BM25 混合检索。
- 演练必须支持真正动态的多轮追问。
- 讲稿必须可编辑和持久化。
- 长期记忆必须支持跨会话、跨课次使用。

### P06：所有重要结论必须有证据

Agent 不得仅根据教师回答流畅程度判断知识已经掌握。

资料引用、能力评估和教学历史都应保留证据来源。

# 2. 目标用户与使用场景

## 2.1 目标用户

### 核心用户：专业知识教师

典型特征：

- 需要长期准备多次关联课程。
- 经常从多个来源学习新知识。
- 需要将复杂概念解释给不同基础的学生。
- 需要提前准备学生可能提出的问题。
- 希望积累自己的课程知识体系。
- 对课堂讲解的准确性和专业性有较高要求。

首期以计算机领域教师作为验证群体，但产品模型应尽量保持学科无关。

## 2.2 用户核心任务

| 编号 | 用户任务 | 期望结果 |
|---|---|---|
| JT01 | 研究一个不熟悉的知识主题 | 建立准确、深入的理解 |
| JT02 | 整合不同来源资料 | 获得可引用的知识依据 |
| JT03 | 整理授课内容 | 形成结构完整的讲稿 |
| JT04 | 检验自己是否真正理解 | 找出认知盲点 |
| JT05 | 提前练习回答学生提问 | 增强课堂应对准备 |
| JT06 | 回顾以前讲过的课程 | 避免重复或遗漏知识 |
| JT07 | 记录课堂实际发生的情况 | 改善后续教学 |
| JT08 | 长期积累个人教学资产 | 降低未来备课成本 |

## 2.3 典型使用情境

一位大学计算机教师需要准备 90 分钟的 Redis 分布式锁课程。

教师通过上传 PDF、DOCX 和技术文档 URL，使用学习模式深入研究锁机制、过期时间、自动续期和 fencing token。

完成研究后，教师整理出完整讲稿。

随后切换演练模式，Agent 模拟学生提出问题，教师独立作答。Agent 根据教师的回答连续追问，直到完成演练或教师主动退出。

演练报告指出教师对锁过期后的旧持有者风险理解不足。

教师返回学习模式补充知识，修改讲稿，并重新进行相关演练。

授课结束后，教师记录实际教学进度和学生提出的问题。

两周后准备数据库并发控制课程时，系统自动发现新课程与历史内容的关联，提醒教师复习曾经出现的知识漏洞，并建议课堂衔接方式。

# 3. 用户旅程（User Journey）

## 3.1 端到端用户旅程总览

用户旅程分为八个主要阶段：

**建立课次 → 导入资料 → 探索学习 → 整理讲稿 → 课堂演练 → 补强与确认 → 实际授课 → 复盘与下一次备课。**

这不是必须严格线性执行的流程。

教师可以在学习、讲稿编辑和演练之间反复切换，直至认为已经达到授课准备要求。

## 3.2 完整用户旅程表

| 阶段 | 用户目标和行为 | 系统交互 | 产出与记忆 | 主要风险 |
|---|---|---|---|---|
| 1. 创建课次 | 输入主题、授课目标、时长、学生背景 | 建立课次工作区，查询历史相关课程 | 课次上下文 | 输入过多导致放弃 |
| 2. 导入资料 | 上传 PDF、DOCX，添加 URL | 解析资料，建立索引，显示处理结果 | 可检索资料库 | 文档解析错误 |
| 3. 知识学习 | 多轮提问、讨论、验证结论 | 解释知识、检索证据、提出探索建议 | 学习记录、候选知识记忆 | AI 错误解释 |
| 4. 教学整理 | 确定大纲并生成完整讲稿 | 整理知识、设计教学顺序、编辑文档 | 大纲与讲稿版本 | 讲稿与理解脱节 |
| 5. 课堂演练 | 点击开始演练，逐题回答 | Agent 主动提问并动态追问 | 演练记录、能力证据 | 追问机械、错误评价 |
| 6. 补强准备 | 查看反馈、补充学习、再次演练 | 定位薄弱点，建议复习内容 | 更新的知识状态与讲稿 | 无休止演练 |
| 7. 实际授课 | 教师独立授课 | 无需实时 Agent 辅助 | 授课行为发生在系统外 | 实际进度与讲稿不同 |
| 8. 复盘与延续 | 记录课堂情况，准备下一课 | 更新教学历史，关联新课知识 | 长期教学记忆 | 错误记录或遗忘复盘 |

## 3.3 用户旅程 A：首次使用与备课

### 目标

让首次用户在最少配置下建立可用的备课工作区。

### 详细步骤

**A01：进入产品**

用户进入工作台，看到创建课程入口。

首次使用不要求填写详细教师档案。

**A02：创建课程**

用户输入：

- 课程名称，例如《Redis 核心技术》。
- 简要课程目标。
- 可选的教学对象描述。

**A03：创建课次**

输入：

- 课次主题：Redis 分布式锁。
- 授课时长：90 分钟。
- 学生基础：已学习 Redis 基本数据结构和原子操作。
- 本次目标：理解分布式锁及其局限性。

**A04：进入学习模式**

系统默认进入学习模式。

界面提示用户导入资料，或者开始围绕主题讨论。

**A05：导入资料**

用户上传资料或输入 URL。

系统显示处理状态、资料目录和解析结果。

**A06：开始知识研究**

用户发起提问：

「Redis 分布式锁究竟解决什么问题？」

Agent 根据资料回答，并提供来源引用。

**A07：继续深入讨论**

用户针对回答追问：

「为什么不能只用数据库事务？」

Agent 对比两者解决的问题，并根据需要检索资料。

**A08：生成初步大纲**

用户要求根据当前研究内容整理 90 分钟教学大纲。

Agent 生成结构化大纲，并允许编辑。

**A09：生成讲稿**

教师确认大纲后，系统生成完整讲稿。

用户可以继续研究某个知识点，并将新的解释插入讲稿。

### 完成标准

用户获得一份可编辑、可保存且有来源依据的完整讲稿，并能够继续围绕其内容展开讨论。

## 3.4 用户旅程 B：课堂演练

### 目标

在没有实时学习辅助的情况下，检验教师是否能够独立回应学生问题。

### 详细步骤

**B01：切换至演练模式**

用户在当前课次中选择「演练」。

系统显示演练待开始界面。

此时：

- 不展示底部聊天输入框。
- 不自动生成第一轮问题。
- 页面中央展示「开始演练」按钮。
- 可展示本次演练将覆盖的课次主题和简短说明。

**B02：点击开始演练**

用户点击「开始演练」。

系统创建一次演练会话，加载当前课次、教学目标、历史知识薄弱点等上下文。

Agent 自动生成并展示第一个问题。

教师无需输入「开始提问」等指令。

**B03：回答问题**

教师在问题下方的回答输入框中作答。

可以使用自由文本回答。

提交后，系统保存原始回答。

**B04：Agent 分析回答**

Agent 在后台分析：

- 是否回答了当前问题。
- 是否存在关键事实错误。
- 是否遗漏重要前提。
- 是否存在需要验证的推断。
- 是否需要继续追问。

**B05：动态追问**

Agent 根据教师的具体回答选择下一步：

- 深入追问当前知识点。
- 引入反例。
- 改变条件。
- 切换知识点。
- 结束演练。

**B06：重复进行**

系统循环执行「提问 → 回答 → 分析 → 决策」。

**B07：结束演练**

存在两种结束方式：

- Agent 判断演练目标达到，主动结束。
- 教师点击「结束演练」，主动退出。

**B08：查看演练报告**

系统展示：

- 已演练知识点。
- 完成情况。
- 回答中的关键问题。
- 正确理解的内容。
- 尚未验证的知识。
- 建议复习的内容。

教师可以选择返回学习模式，或者再次演练。

### 完成标准

用户能够不依赖自由聊天指令，完成一场由 Agent 主导的连续问答演练。

---

## 3.5 用户旅程 C：演练发现问题后返回学习

### 目标

将演练暴露的问题转化为有针对性的学习任务。

### 详细步骤

1. 演练发现教师未能解释锁过期后的并发风险。
2. 系统记录原始回答和评估依据。
3. 演练结束后，展示「复习该知识点」入口。
4. 教师点击入口，返回学习模式。
5. Agent 自动带入本次错误问题和相关资料。
6. 教师继续讨论相关原理。
7. 教师确认理解后，重新进入演练。
8. 系统生成具有不同条件的变式问题。
9. 根据新的独立回答更新验证记录。

### 关键业务规则

学习模式中的解释和提示不能直接作为演练通过的证据。

系统应保留首次失败及后续通过的记录，以展示知识理解变化，而不是覆盖历史。

---

## 3.6 用户旅程 D：第二次备课与长期记忆

### 目标

验证长期记忆能否真正减少重复学习，并改善课程衔接。

### 前提

教师已经完成 Redis 分布式锁课程，并记录实际授课情况。

### 详细步骤

1. 教师创建新的课次「数据库并发控制」。
2. 系统查询当前课程、班级及教师历史记录。
3. 检索发现相关历史知识。
4. Agent 提示曾经讲授的 Redis 锁相关内容。
5. Agent 区分已讲授、未讲授以及未经验证的学生理解状态。
6. Agent 检索教师此前关于并发问题的演练记录。
7. 如果发现相关历史弱点，建议教师进行简短复测。
8. 教师接受或忽略建议。
9. Agent 基于实际教学历史生成本次课程衔接建议。
10. 用户继续开展新的学习、讲稿整理和演练。

### 完成标准

即使开始了新的会话，Agent 仍能正确利用历史教学事实和教师能力记录，并能追溯其来源。

# 4. 信息架构与导航

## 4.1 一级导航

MVP 建议采用以下信息架构：

**工作台**

- 最近课程
- 最近课次
- 继续备课
- 待复习知识

**我的课程**

- 课程列表
- 课次列表
- 课程资料
- 教学产物
- 历史授课记录

**教学记忆**

- 教师知识记录
- 历史薄弱点
- 教学经验
- 跨课程关联

MVP 不单独建立复杂的知识图谱页面。

## 4.2 课次工作台

进入课次后，以顶部模式切换为核心：

**学习 | 演练**

两种模式共享：

- 当前课程。
- 当前课次。
- 相关资料。
- 教师知识状态。
- 长期记忆。

但是两种模式使用不同交互界面。

# 5. 学习模式需求

## 5.1 页面布局

学习模式采用知识研究工作台结构。

**左侧：资料与课次导航**

展示：

- 当前课次。
- 已导入资料。
- 资料章节。
- 相关历史课程。

**中央：多轮对话区域**

展示：

- 教师输入。
- Agent 回答。
- 检索引用。
- 相关操作。

页面底部保留固定输入框。

**右侧：教学内容工作区**

展示：

- 知识笔记。
- 课程大纲。
- 完整讲稿。

右侧工作区允许折叠，避免影响对话空间。

## 5.2 对话行为

### FR-L01：教师主动提问

用户可围绕课次自由提问。

Agent 根据上下文判断是否需要检索资料和长期记忆。

### FR-L02：知识解释

Agent 应支持：

- 概念解释。
- 原理推导。
- 案例说明。
- 条件分析。
- 反例构造。
- 多种观点比较。

### FR-L03：主动引导

Agent 可以根据研究进度提出进一步探索建议，但不应频繁打断教师。

### FR-L04：来源引用

资料性结论应尽可能展示可定位的来源。

### FR-L05：知识记录

用户可以将重要结论保存到知识笔记。

### FR-L06：讲稿联动

用户可以将经过讨论的内容添加到讲稿，或者要求局部修改。

### FR-L07：历史记忆

Agent 可以结合历史课程和教师曾经的知识问题提供建议。

### FR-L08：会话延续

用户离开后重新进入课次，应能够恢复相关上下文。

# 6. 演练模式需求

## 6.1 设计定位

演练模式不是另一个聊天窗口，而是一套由 Agent 主导的任务执行界面。

核心机制：

**Agent 主动提问 → 教师独立回答 → Agent 评估并决定下一轮 → 完成或主动退出。**

## 6.2 页面状态

### 状态 A：待开始

主界面展示：

- 演练标题。
- 当前课次。
- 演练说明。
- 「开始演练」按钮。

**不显示底部输入框。**

切换进入演练模式本身不创建演练记录。

只有点击「开始演练」后才创建实际演练会话。

### 状态 B：准备中

点击开始后：

- 创建演练会话。
- 加载课程与知识上下文。
- 生成第一个问题。

显示准备状态。

生成失败时支持重试或返回。

### 状态 C：进行中

页面展示：

- 当前轮次。
- 模拟学生问题。
- 历史问答记录。
- 教师回答输入框。
- 提交回答按钮。
- 结束演练按钮。

每轮默认只提出一个主要问题。

### 状态 D：分析中

教师提交回答后：

- 禁止重复提交。
- 保存回答。
- Agent 分析回答。
- 决定下一步。

分析过程不默认展示标准答案。

### 状态 E：已结束

隐藏回答输入框。

展示演练完成状态及总结报告。

提供：

- 查看完整报告。
- 返回学习模式。
- 再次演练。

## 6.3 动态追问规则

### FR-R01：首轮问题

Agent 根据课次目标、知识点和历史记录生成首轮问题。

### FR-R02：答案分析

Agent 对教师回答进行事实、逻辑和完整性分析。

### FR-R03：下一步决策

至少支持以下结果：

- `FOLLOW_UP`：继续追问。
- `CHALLENGE`：引入反例或质疑。
- `NEXT_TOPIC`：切换知识点。
- `COMPLETE`：结束演练。

### FR-R04：动态生成

下一轮问题必须参考本轮回答。

不得仅通过固定问题数组模拟动态追问。

### FR-R05：隐性评估

演练过程中默认不逐题公布标准答案，避免影响后续独立表现。

### FR-R06：教师主动退出

教师可随时结束演练。

已提交的回答应保存。

尚未提交的回答默认不作为有效评估证据。

主动退出的状态为 `EXITED`，不能视为完成。

### FR-R07：Agent 主动结束

当预定目标得到足够验证，或达到合理的轮次限制时，Agent 可以结束。

**轮次上限属于运行保护机制，不代表演练通过。**

### FR-R08：演练反馈

演练结束后生成可追溯的总结。

### FR-R09：复习衔接

从报告中可以直接跳转到学习模式，继续研究薄弱知识。

## 6.4 演练状态机

```text
IDLE
  |
  | 开始演练
  v
PREPARING
  |
  v
ASKING
  |
  v
WAITING_ANSWER
  |
  | 提交回答
  v
EVALUATING
  |
  +-- FOLLOW_UP ----> ASKING
  |
  +-- CHALLENGE ----> ASKING
  |
  +-- NEXT_TOPIC ---> ASKING
  |
  +-- COMPLETE -----> COMPLETED

教师主动退出：
PREPARING / ASKING /
WAITING_ANSWER / EVALUATING
  |
  v
EXITED
```

若 Agent 请求仍在执行，用户退出后返回的过期结果不得继续推进已经退出的演练。应通过会话版本或运行状态进行校验。

## 6.5 演练自动结束策略

Agent 不应单纯根据轮次决定是否通过。

建议综合考虑：

1. 本次演练的知识覆盖程度。
2. 关键知识是否得到验证。
3. 是否仍然存在值得追问的明显漏洞。
4. 教师是否已经回答过足够的变式问题。
5. 继续追问是否具有新增信息价值。

MVP 可设置较小的默认演练规模，例如 3～8 个主要问题，并允许根据需要扩展。

演练结束状态不等于全部知识通过。

## 6.6 评估记录

每轮至少保存：

- 问题。
- 教师原始回答。
- 关联知识点。
- 评估结论。
- 评估证据。
- 发现的问题。
- 下一轮决策原因。

对于知识错误，系统应提供可以核查的解释或资料依据。

# 7. 资料管理与 RAG 检索

## 7.1 支持的数据来源

MVP：

- PDF
- DOCX
- Web URL
- Markdown / TXT

网页抓取失败、需要登录或访问受限时，应明确提示。

## 7.2 文档处理

处理流程：

1. 上传或获取资料。
2. 提取正文及结构信息。
3. 识别标题、章节、表格和代码。
4. 将文档转换为统一内部结构。
5. 基于章节进行分片。
6. 建立向量索引和关键词索引。
7. 保存原始文档定位信息。

对扫描 PDF、复杂公式和表格，允许使用专门解析或 OCR 工具，但需要明确解析结果的可信度。

## 7.3 检索架构

**MVP 最低要求：混合检索。**

采用：

- Dense Retrieval：语义向量检索。
- Sparse Retrieval：BM25。
- Fusion：RRF 排名融合。
- Metadata Filter：范围过滤。
- Evidence Assembly：来源与上下文组装。

初期不引入图谱检索。

## 7.4 检索范围

支持：

- 当前资料。
- 当前课次所有资料。
- 当前课程所有资料。
- 经授权的历史课程资料。

默认优先当前课次，只有需要跨课程关联时才扩大范围。

## 7.5 二次检索

Agent 发现检索结果不足时，可以：

- 重新生成查询。
- 扩展关键词。
- 调整检索范围。
- 查找前置知识。
- 查找相邻章节。

必须设置检索次数和资源消耗限制，避免无意义循环。

## 7.6 检索验收

建立人工标注的知识问答集，测试：

- Recall@K。
- 引用定位正确率。
- 无证据问题的拒答或不确定性表达。
- 关键知识遗漏率。

建议首期以 Recall@10 ≥ 85% 作为待验证目标，但需要明确测试集构成，不能凭单一数字判断系统整体可靠。

# 8. 教学大纲与讲稿

## 8.1 生成教学大纲

Agent 根据以下信息生成：

- 课程目标。
- 授课时长。
- 学生基础。
- 教师确认的教学重点。
- 已研究知识。
- 资料内容。
- 相关历史课程。

输出结构包含章节、知识点、时间建议、案例及过渡关系。

教师可以调整大纲顺序和范围。

## 8.2 完整讲稿

讲稿不仅是标题和要点列表。

应包含：

1. 开场引入。
2. 上节课回顾。
3. 教学目标。
4. 概念讲解。
5. 原理说明。
6. 推导和案例。
7. 适合课堂使用的提问。
8. 常见误区。
9. 章节过渡。
10. 课堂总结。
11. 后续课程预告。
12. 教师内部备忘。

## 8.3 内容分层

讲稿应区分：

**授课正文**

教师可以直接用于教学的内容。

**教师备忘**

对可能遇到的高阶追问、知识边界和特殊案例的准备。

两者可以在同一个编辑器中管理，但导出时允许选择。

## 8.4 编辑与持久化

MVP 必须支持：

- 手动编辑。
- 章节级 AI 修改。
- 自动保存或可靠的保存反馈。
- 历史版本。
- 重新进入后继续编辑。
- DOCX 导出。

PDF 导出可以使用统一的文档渲染能力实现。

## 8.5 演练与讲稿联动

演练发现问题后，可定位到对应讲稿章节。

用户可以要求 Agent 建议修订内容。

**不能因为演练结果存在错误就自动覆盖教师已经确认的讲稿。**

# 9. 长期记忆需求

## 9.1 记忆目标

长期记忆必须支持：

- 会话恢复。
- 教师知识状态更新。
- 历史认知漏洞回顾。
- 跨课程知识关联。
- 已授课内容查询。
- 后续学习和演练策略调整。

## 9.2 记忆分类

### A. 教师记忆

- 教学偏好。
- 已验证知识。
- 待复习知识。
- 历史错误认识。
- 独立演练表现。

### B. 课程记忆

- 课程知识点。
- 已准备课次。
- 历史资料。
- 大纲和讲稿版本。
- 知识关联。

### C. 班级记忆

- 已实际讲授知识。
- 未完成内容。
- 真实学生提问。
- 教学反馈。

### D. 教学经验记忆

- 有效案例。
- 低效解释。
- 时间安排经验。
- 教师确认的改进方法。

## 9.3 记忆写入策略

### 显式写入

用户主动要求记住某个结论、偏好或教学经验。

### 自动记录

结构化业务事件自动保存，例如：

- 演练完成。
- 讲稿更新。
- 教师确认授课进度。

### 候选记忆

Agent 从对话中发现值得长期保存的内容时，先生成候选记录。

重要且无法通过工具直接验证的事实应由教师确认。

## 9.4 记忆检索策略

### 主动加载

进入课次时加载：

- 当前课程背景。
- 教师主要偏好。
- 当前任务进度。
- 最近相关知识问题。

### 按需检索

当用户讨论某个知识点时，系统查找：

- 历史相关课程。
- 相似知识问题。
- 以往错误记录。
- 已有解释和教学案例。

## 9.5 记忆冲突与更新

支持：

- 纠正记忆。
- 更新能力状态。
- 标记记录过期。
- 保留变更历史。
- 删除不需要的记忆。
- 避免重复记录同一个事实。

## 9.6 能力证据等级

| 状态 | 含义 |
|---|---|
| NOT_ASSESSED | 尚无验证 |
| EXPOSED | 已接触或研究 |
| GUIDED | 在引导下完成 |
| INDEPENDENT | 独立通过 |
| TRANSFER_VERIFIED | 在新情境中独立通过 |
| NEEDS_REVIEW | 发现需要复习的问题 |

实际数据模型中，验证结果和最新能力判断应分别存储，防止历史错误记录被覆盖。

## 9.7 记忆质量约束

以下推断不允许自动成立：

- 讲稿包含知识 → 教师掌握知识。
- 教师学过知识 → 教师独立通过。
- 教师讲过知识 → 学生掌握知识。
- AI 提出建议 → 教师已经实施。
- AI 模拟学生表现 → 真实学生会有同样表现。

建议的核心实体如下：

| Class | id、courseId、background |
| Lesson | id、courseId、title、status、duration |
| Source | id、type、uri、contentHash、parseStatus |

| Message | id、sessionId、role、content |
| Rehearsal | id、lessonId、status、startedAt、endedAt |
| RehearsalTurn | id、rehearsalId、question、answer、evaluation |

| Artifact | id、lessonId、type、version、content |

## 10.1 会话与演练的关系

学习会话采用普通多轮对话模式。

演练会话需要独立的业务状态，并可以关联通用消息记录。

**不应仅依靠最后一条聊天消息判断当前演练进度。**

例如演练已经进入 `WAITING_ANSWER`，该状态应由业务数据明确表示。

## 10.2 演练轮次的幂等性

每次教师提交回答需要唯一请求标识。

如果网络重试，不得重复生成两轮评估或两道下一轮问题。

## 10.3 教学产物版本

讲稿版本必须能够追溯：

- 对应课次。
- 创建时间。
- 修改来源。
- 内容版本。
- 是否经过教师确认。

# 11. Agent 架构与职责

## 11.1 推荐架构

MVP 优先采用：

**一个主 Agent + 不同模式策略 + 专业工具 + 结构化业务状态。**

无需在初版中强制引入多 Agent 架构。

## 11.2 学习模式策略

Agent 可以：

- 解释知识。
- 查询资料。
- 主动提供建议。
- 比较观点。
- 展开讨论。
- 修改教学产物。

交互以教师意图为主。

## 11.3 演练模式策略

Agent 应：

- 读取本次演练目标。
- 生成问题。
- 等待回答。
- 分析回答。
- 选择下一轮动作。
- 判断是否结束。
- 生成报告。

演练过程中不得默认直接向教师公布参考答案。

## 11.4 评估可靠性

对知识正确性的评估，建议采用：

**原始回答 + 参考证据 + 明确评估维度 + 可复核结论。**

当证据不足或存在合理争议时，使用 `UNCERTAIN` 或同等状态，而不是强行给出正确、错误二选一。

## 11.5 工具能力

MVP 需要覆盖：

- 资料解析。
- 混合检索。
- 历史记忆检索。
- 课程上下文读取。
- 大纲保存与更新。
- 讲稿保存与更新。
- 演练开始与状态更新。
- 演练评估保存。
- 能力证据写入。
- 教学记录保存。

## 11.6 中断恢复

Agent Loop 和工具执行需要具备基本可恢复能力。

至少保存：

- 当前会话。
- 当前演练状态。
- 当前轮次。
- 已提交回答。
- 工具执行结果。
- 已生成产物。

对具有副作用的操作应提供幂等保护。
