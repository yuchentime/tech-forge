# TeachForge 技术功能设计文档

**版本：** V0.2  
**文档类型：** Technical Design Document（TDD）  
**产品：** TeachForge — 教师知识研究与课堂演练 Agent  
**目标平台：** Windows / macOS  
**应用形态：** Electron 桌面应用 + 本地 NestJS 后端  
**编程语言：** TypeScript  
**部署模式：** Local-first，无需独立服务器  
**文档状态：** 技术方案初稿

# 1. 项目目标

## 1.1 产品技术目标

TeachForge 是一款帮助教师研究知识、准备讲稿、完成课前问答演练，并通过长期记忆积累教学经验的桌面应用。

系统需要支持以下完整业务链路：

1. 教师创建课程和课次。
2. 导入 PDF、DOCX、URL 等知识资料。
3. 系统解析资料并建立本地混合检索索引。
4. 教师使用学习模式进行多轮知识讨论。
5. 教师整理大纲和完整讲稿。
6. 教师切换演练模式，点击「开始演练」。
7. Agent 主动提问，教师逐轮回答。
8. Agent 根据回答动态追问、切换知识点或结束演练。
9. 系统生成具有证据依据的演练报告。
10. 教师记录实际授课情况。
11. 后续备课时检索历史课程、知识状态和教学经验。

## 1.2 技术设计原则

### 本地优先

业务后端、文档解析、向量化、知识检索、数据库及长期记忆均在用户电脑中运行。

不需要用户部署远程服务器。

### 独立后端

使用 NestJS 承载全部核心业务。

Electron Main 不直接实现课程管理、RAG、Agent Loop 或长期记忆等业务。

### 用户自配 LLM

系统不绑定某一家模型供应商。

用户自行配置模型 API 地址、密钥与模型名称。

### 混合检索下限

MVP 必须同时支持向量检索与 BM25。

不得使用纯向量检索作为最终交付方案。

### 有状态 Agent

学习会话、演练轮次、工具调用和执行任务均需要持久化业务状态。

### 最小可用

初期控制模块数量，但核心流程必须具备真实使用价值。

不以「按钮可点击」「模型能回复」作为完整功能验收标准。

# 3. 整体系统架构

## 3.1 进程架构

系统分为三个主要运行部分。

### Electron Renderer

负责：

- React 页面。
- 用户交互。
- 学习与演练模式切换。
- 文档编辑。
- 流式消息展示。
- 本地任务进度展示。

### Electron Main

负责：

- 应用生命周期。
- 窗口管理。
- 启动 NestJS 后端。
- 后端进程监控。
- 后端异常恢复。
- 系统文件选择器。
- 后端启动令牌与端口管理。
- 应用退出时的资源清理。

负责：

- 课程和课次。
- 资料解析及索引。
- RAG。
- Agent Runtime。
- LLM Provider。
- 演练状态机。
- 讲稿管理。
- 长期记忆。
- SQLite。
- 本地后台任务。

## 3.3 进程隔离原则

NestJS 应作为独立 OS 进程运行，而不是在 Electron Main 中直接调用 `NestFactory.create()`。

这样可以：

- 独立调试后端。
- 隔离异常。
- 保持 Main Process 轻量。
- 独立管理后台计算。
- 复用后端业务代码。

后端逻辑不得直接依赖 Electron API。

# 4. Electron 与 NestJS 生命周期

## 4.1 启动机制

推荐优先验证 Electron `utilityProcess.fork()` 启动 NestJS 编译后的 Node.js 入口。

如果实际打包测试发现原生依赖或运行环境兼容问题，再评估随应用打包专用 Node.js Runtime 并通过 `spawn()` 启动。

无论选择哪种机制，用户都不需要手动安装 Node.js。

## 4.2 应用启动流程

```text
启动 TeachForge
      │
      ▼
Electron Main Ready
      │
      ▼
初始化本地数据目录
      │
      ▼
生成本次运行的认证令牌
      │
      ▼
启动 NestJS Backend
      │
      ▼
打开 SQLite / 执行 Migration
      │
      ▼
注册业务模块和 HTTP 服务
      │
      ▼
监听 127.0.0.1 动态端口
      │
      ▼
通知 Electron：BACKEND_READY
      │
      ▼
显示 React 主界面
```

## 4.3 后端启动要求

后端应：

1. 仅绑定 `127.0.0.1`。
2. 使用动态分配的端口。
3. 在准备完成后主动向父进程发送就绪消息。
4. 传递实际监听端口。
5. 提供健康检查接口。
6. 记录启动失败原因。
7. 避免将数据库初始化失败误报为正常就绪。

推荐通过 Utility Process 的父子进程消息通道通知 Electron。

不要仅依赖固定时间延迟判断后端已启动。

## 4.4 后端启动代码示意

Electron Main：

```ts
import { app, utilityProcess } from 'electron';
import path from 'node:path';

async function startBackend() {
  const backendPath = path.join(
    process.resourcesPath,
    'backend',
    'main.cjs'
  );

  const backend = utilityProcess.fork(
    backendPath,
    [],
    {
      stdio: 'pipe',
      env: {
        ...process.env,
        TEACHFORGE_DATA_DIR: app.getPath('userData'),
        TEACHFORGE_HOST: '127.0.0.1',
        TEACHFORGE_PORT: '0'
      }
    }
  );

  backend.on('message', (event) => {
    if (event.type === 'backend.ready') {
      console.log('Backend ready', event.port);
    }
  });

  backend.on('exit', (code) => {
    console.error('Backend exited', code);
  });

  return backend;
}
```

该代码为启动结构示例，不是可直接交付的完整进程管理器。

实际实现还需要处理打包路径、启动令牌安全传递、启动超时、进程异常与退出竞态。

## 4.5 NestJS Bootstrap

推荐使用 Fastify Adapter：

```ts
import { NestFactory } from '@nestjs/core';
import {
  FastifyAdapter,
  NestFastifyApplication
} from '@nestjs/platform-fastify';
import { AppModule } from './app.module';

async function bootstrap() {
  const app =
    await NestFactory.create<NestFastifyApplication>(
      AppModule,
      new FastifyAdapter()
    );

  app.setGlobalPrefix('api');

  await app.listen(0, '127.0.0.1');

  const address = app.getHttpServer().address();

  // 在完成应用就绪检查后，
  // 通过父子进程通道通知 Electron。
  process.parentPort?.postMessage({
    type: 'backend.ready',
    port: address.port
  });
}

bootstrap();
```

仅作为 Utility Process 场景的实现示意。

正式代码必须处理启动失败、监听地址类型校验、令牌注册及优雅退出。

## 4.6 后端异常恢复

Electron Main 需要监听：

- 后端启动失败。
- 后端进程退出。
- 健康检查失败。
- 应用主动关闭。

发生异常时：

1. 标记后端不可用。
2. 前端进入重连状态。
3. 保存错误日志。
4. 根据错误类型决定是否重启。
5. 进行有限次数自动恢复。
6. 失败后展示诊断信息。

不能无限重启。

对于数据库损坏或 Migration 失败，不应通过不断重启掩盖问题。

## 4.7 应用退出

建议：

1. 停止接受新的业务任务。
2. 请求取消或挂起运行中的 Agent。
3. 保存必要的状态。
4. 等待允许的清理时间。
5. 关闭 SQLite。
6. 终止 NestJS 进程。
7. 退出 Electron。

若强制关闭，下一次启动根据数据库记录恢复状态。

# 5. 通信架构

## 5.1 通信协议

确定采用：

**REST API + SSE。**

REST 用于：

- CRUD。
- 资料管理。
- 演练开始。
- 回答提交。
- 任务取消。
- 讲稿保存。
- 长期记忆查询。

SSE 用于：

- 学习对话流式输出。
- Agent 执行事件。
- 演练问题生成。
- 演练分析进度。
- 任务状态通知。

MVP 不引入 WebSocket。

## 5.2 安全通信边界

虽然 HTTP 服务只运行在 localhost，但仍需要防止其他本地程序及恶意网页访问。

建议：

- 动态端口。
- 每次启动生成高熵认证令牌。
- 所有业务 API 强制认证。
- 严格 Origin 校验。
- 禁止任意跨域访问。
- 使用 Electron Preload 提供受控业务 API。
- 不将认证令牌暴露给普通 Renderer JavaScript。

推荐由 Electron Main 负责携带凭据访问本地后端，并通过 Preload 将受控请求和事件流转发给 React。

这意味着 React 不需要直接持有 NestJS 的认证令牌。

## 5.3 REST API

建议基础接口：

| Method | Endpoint | 功能 |
|---|---|---|
| GET | `/api/health` | 后端健康检查 |
| GET | `/api/courses` | 查询课程 |
| POST | `/api/courses` | 创建课程 |
| POST | `/api/lessons` | 创建课次 |
| POST | `/api/documents/import` | 导入资料 |
| GET | `/api/documents/:id` | 资料详情 |
| POST | `/api/conversations/:id/messages` | 发送用户消息 |
| POST | `/api/rehearsals` | 开始演练 |
| POST | `/api/rehearsals/:id/answers` | 提交回答 |
| POST | `/api/rehearsals/:id/exit` | 退出演练 |
| GET | `/api/rehearsals/:id` | 演练状态 |
| GET | `/api/rehearsals/:id/report` | 演练报告 |
| PUT | `/api/artifacts/:id` | 保存教学产物 |
| GET | `/api/memories` | 记忆查询 |
| PATCH | `/api/memories/:id` | 修改记忆 |

接口属于初步设计，详细参数在 API Schema 阶段确定。

## 5.4 SSE 事件

统一事件结构：

```ts
interface StreamEvent {
  eventId: string;
  runId: string;
  sequence: number;
  type: string;
  timestamp: string;
  payload: unknown;
}
```

事件类型包括：

- `run.started`
- `message.delta`
- `message.completed`
- `tool.started`
- `tool.completed`
- `rehearsal.question`
- `rehearsal.evaluation.completed`
- `rehearsal.completed`
- `run.failed`

REST 请求与 SSE 订阅应通过 `runId` 关联。

SSE 断线后应查询服务端任务状态，并根据已持久化事件进行必要的恢复。

不能将 SSE 连接本身作为业务状态来源。

| RehearsalModule | 演练状态机、主动提问 |

| HealthModule | 就绪和健康检查 |

## 6.3 NestJS 依赖约束

建议的依赖关系：

```text
Controllers
    ↓
Application Services
    ↓
Domain Interfaces
    ↓
Infrastructure Adapters
```

Controller 只负责：

- 接收请求。
- 校验参数。
- 调用 Service。
- 返回结果。

不要把完整 Agent Loop 写在 Controller 中。

## 6.4 避免模块循环依赖

AgentModule 可通过接口调用 Retrieval、Memory 和 Artifact 等能力。

不建议让 MemoryModule 反向依赖整个 AgentModule。

例如 MemoryModule 应暴露：

```ts
interface MemoryService {
  search(input: MemoryQuery): Promise<MemoryHit[]>;
  propose(input: MemoryCandidate): Promise<void>;
  confirm(id: string): Promise<void>;
}
```

Agent 通过工具适配器调用这些业务服务。

# 8. 文档解析与知识索引

## 8.1 导入模块

支持：

- PDF。
- DOCX。
- URL。
- TXT。
- Markdown。

统一转换为可引用的内部文档结构。

需要保留来源位置和解析异常。

## 8.2 索引流程

```text
Import Document
      ↓
Parse Content
      ↓
Normalize Structure
      ↓
Chunking
      ↓
Save Chunks
      ↓
      ├── BM25 Index
      └── Local Embedding
                 ↓
            Vector Index
```

## 8.3 Chunking

采用：

**标题结构优先 + 长度限制 + 必要的 Overlap。**

初期可使用约 400～600 tokens 作为实验参数。

需要保存：

- Document ID。
- Version ID。
- Section Path。
- Page。
- Chunk Index。
- Text。
- Token Count。

## 8.4 索引一致性

业务原文与索引应采用明确的状态管理。

文档分片保存成功后，索引任务可以异步执行。

索引失败时标记 `INDEX_FAILED`，允许重新执行。

不要将未完成索引的资料显示为完全可检索。

# 9. 本地 Embedding

## 9.1 实现

NestJS EmbeddingModule 通过 Worker 调用 Transformers.js。

模型运行在用户设备中。

默认不使用第三方 Embedding API。

## 9.2 执行模式

推荐：

- 首次使用时加载模型。
- 后台批量计算文档向量。
- 对查询进行单条或小批量计算。
- 缓存模型实例。
- 支持任务取消。
- 避免阻塞 NestJS HTTP 事件循环。

## 9.3 模型管理

保存：

- 模型 ID。
- 模型版本。
- 向量维度。
- 归一化策略。
- 本地路径。
- 索引版本。

更换模型后，需要重建对应向量索引。

# 10. 本地混合检索

## 10.1 检索架构

MVP 确定：

**sqlite-vec + FTS5 BM25 + RRF。**

```text
Search Query
     │
     ├── Dense Retrieval
     │       ↓
     │    sqlite-vec
     │
     └── Sparse Retrieval
             ↓
          FTS5 BM25
             │
             ▼
         RRF Fusion
             │
             ▼
       Metadata Filtering
             │
             ▼
      Evidence Assembly
             │
             ▼
          Agent
```

实际执行时，应尽可能将课程、文档等范围限制提前应用于两路召回，避免全局 TopK 截断导致目标课程证据丢失。

## 10.2 中文检索

FTS5 默认分词不足以满足完整的中文词语级 BM25 需求。

MVP 应实现统一的中文查询与文档分词策略。

尤其需要测试：

- 中文概念。
- 中英文混合问题。
- 技术缩写。
- API 名称。
- Redis 等专有术语。

## 10.3 检索服务接口

```ts
interface RetrievalService {
  search(input: {
    query: string;
    courseId?: string;
    lessonId?: string;
    documentIds?: string[];
    topK?: number;
  }): Promise<RetrievalHit[]>;
}
```

返回结果必须包含可追溯来源。

## 10.4 检索不足处理

Agent 可以重新构造查询并再次检索。

但必须控制：

- 最大检索次数。
- 上下文 Token。
- 检索范围。
- 任务成本。

MVP 可以暂不引入独立 Rerank。

待测量质量后再决定是否增加。

# 12. Agent Runtime

## 12.1 设计

采用自研 TypeScript Agent Runtime。

建议作为 NestJS 的 AgentModule 及独立核心逻辑包实现。

## 12.2 组件

```text
AgentRuntime
├── ContextBuilder
├── LLMProvider
├── ToolRegistry
├── ToolExecutor
├── RunStateManager
├── EventRepository
└── RunController
```

## 12.3 两种运行策略

### Learning Strategy

教师主导。

Agent 可以：

- 解释。
- 检索。
- 深入讨论。
- 提出建议。
- 更新教学产物。

### Rehearsal Strategy

Agent 主导。

Agent 负责：

- 选择知识点。
- 生成问题。
- 分析回答。
- 决定下一轮。
- 结束演练。
- 生成报告。

可以共用底层 LLM、工具执行与上下文构建能力，但需要独立的任务策略。

## 12.4 状态持久化

记录：

- 当前 Run。
- 当前步骤。
- 用户消息。
- 工具调用。
- 工具结果。
- 任务结果。
- 错误状态。

Agent Loop 每次运行可以结束，但业务演练可以继续保持 `WAITING_ANSWER` 状态。

## 12.5 Tool 失败

工具调用状态至少包含：

- PENDING。
- RUNNING。
- SUCCEEDED。
- FAILED。
- UNKNOWN。

工具调用前持久化执行意图，调用后持久化结果。

对于执行结果未知的副作用操作，不能自动重复调用。

# 14. 演练模式

## 14.1 界面规则

**切换到演练模式后，主界面只显示演练说明和「开始演练」入口，不显示底部输入框。**

只有点击「开始演练」才创建实际演练实例。

## 14.2 交互流程

```text
进入演练模式
      ↓
显示开始演练按钮
      ↓
用户点击开始
      ↓
Agent 主动生成第一题
      ↓
教师回答
      ↓
Agent 分析
      ↓
继续追问 / 切换主题 / 结束
      ↓
生成演练报告
```

## 14.3 状态机

```ts
type RehearsalStatus =
  | 'PREPARING'
  | 'ASKING'
  | 'WAITING_ANSWER'
  | 'EVALUATING'
  | 'COMPLETED'
  | 'EXITED'
  | 'FAILED';
```

未开始状态可完全由前端表示。

## 14.4 动态决策

每轮 Agent 返回：

```ts
interface RehearsalDecision {
  action:
    | 'FOLLOW_UP'
    | 'CHALLENGE'
    | 'NEXT_TOPIC'
    | 'COMPLETE';

  assessment: {
    status:
      | 'CORRECT'
      | 'PARTIAL'
      | 'INCORRECT'
      | 'UNCERTAIN';
    issues: string[];
    evidence: string[];
  };

  nextQuestion?: string;
  reason: string;
}
```

通过 Zod 验证。

输出无效时有限重试。

不能使用固定问题数组替代动态追问逻辑。

## 14.5 教师主动退出

退出时：

1. 更新状态为 `EXITED`。
2. 取消当前 Run。
3. 忽略迟到的 Agent 结果。
4. 保留已提交的回答。
5. 记录退出时间。

## 14.6 自动结束

Agent 根据：

- 知识覆盖情况。
- 回答正确性。
- 已发现的薄弱点。
- 后续追问价值。
- 任务规模限制。

决定是否完成演练。

演练完成不代表教师全部知识通过。

## 14.7 演练报告

报告至少包含：

- 本次演练主题。
- 已覆盖知识点。
- 回答正确的部分。
- 错误或遗漏。
- 证据依据。
- 未验证知识。
- 建议复习内容。

报告应支持跳转回学习模式。

# 15. 长期记忆

## 15.1 存储架构

采用：

**SQLite 结构化记忆 + 原始事件记录 + 本地混合检索。**

不建立独立记忆数据库服务。

## 15.2 记忆类型

### 教师记忆

教师偏好、知识状态、认知盲点。

### 课程记忆

知识点、课程关系、教学材料。

### 班级记忆

实际授课内容、学生问题和教学反馈。

### 经验记忆

经过教师确认的有效解释、典型问题和改进建议。

## 15.3 写入策略

来源包括：

- 教师主动保存。
- 演练记录。
- 学习对话候选记忆。
- 课后复盘。
- 讲稿修订。

重要事实必须具备来源。

对于 Agent 推断的长期记忆，保存候选状态，避免直接覆盖已确认事实。

## 15.4 检索机制

分为：

**主动加载**

进入课次时加载当前课程、教学目标和关键历史状态。

**动态检索**

Agent 在研究知识或进行演练时，查询相关历史记忆。

## 15.5 能力证据

能力状态至少区分：

- NOT_ASSESSED。
- EXPOSED。
- GUIDED。
- INDEPENDENT。
- TRANSFER_VERIFIED。
- NEEDS_REVIEW。

演练产生的独立回答证据，不能与学习模式中的受提示回答混淆。

## 15.6 跨课次使用

新课次创建后：

1. 获取班级历史。
2. 查询相关课程。
3. 查询教师已验证知识。
4. 发现相关薄弱点。
5. 生成衔接建议。

MVP 不使用图谱检索。

概念关系可以先在 SQLite 中以结构化关系表存储。

- 判断任务是否幂等。
- 允许安全恢复。
- 对未知副作用任务停止自动重试。

# 18. 安全设计

## 18.1 Electron

必须启用：

- Context Isolation。
- Renderer Sandbox。
- 受控 Preload。
- 关闭不必要的 Node Integration。
- IPC 参数校验。
- 导航与外链限制。

## 18.2 NestJS 本地服务

必须：

- 仅监听 Loopback。
- 使用动态端口。
- 强制业务 API 认证。
- 校验 Origin。
- 限制请求体大小。
- 禁止任意目录文件读取。
- 限制 URL 导入目标。
- 防止未授权本地访问。

## 18.3 数据隐私

用户资料保存在本机。

第三方 LLM 调用可能传输相关资料片段、用户问题和必要记忆。

需要提供明确的数据传输说明。

## 18.4 API Key

采用操作系统安全存储。

不写入普通 JSON 文件。

不输出到日志。

## 18.5 Prompt Injection

资料、网页和检索结果必须视为不可信内容。

不能让文档内的指令直接触发文件读取、数据库修改或其他高权限操作。

# 24. 最终结论

TeachForge 采用：

**Electron + React + NestJS + SQLite + 本地混合检索 + 本地 Embedding + 第三方 LLM API。**

Electron 负责桌面应用生命周期和本地后端进程管理。

NestJS 负责业务服务、Agent Runtime、RAG、长期记忆、演练状态机及全部数据持久化。

前后端通过受控的本地 REST API 和 SSE 通信。

系统不依赖自建服务器，不要求用户安装数据库、Node.js 或 Docker。

架构应同时保证：

1. 日常使用足够简单。
2. 核心业务能够独立测试。
3. 本地数据可靠。
4. Agent 行为可观察、可中断、可恢复。
5. 检索质量满足最小可用要求。
